# Отчёт по оптимизации

## Вариант: 0 (алгоритмы на графах, кратчайшие пути между всеми парами)

в src/slow_code.py это slow_shortest_paths: floyd-warshall на 200 вершинах,
600 случайных рёбер, матрица расстояний как список списков.

замеры: apple m4 pro, macos 26.5.2, cpython 3.13.13, numpy 2.4.4, numba 0.65.0.
каждое время - медиана из 3-5 запусков, time.perf_counter, без профилировщика.

## Исходное профилирование

**Инструмент:** cProfile + pstats, плюс pyinstrument для проверки

**Время выполнения оригинала:** 0.77 сек

**Основные узкие места:**

1. тройной цикл по k, i, j - это 200^3 = 8 млн итераций чистого питона. каждая
   итерация делает четыре индексации списка списков, сложение и сравнение, и всё
   это через интерпретатор. по cProfile на саму функцию приходится 69% времени
   (1.138 из 1.644 сек под профилировщиком), pyinstrument даёт те же 67%.
2. лишний вызов min на каждой итерации (строка new_dist[i][j] = min(...)) - ровно
   8 млн вызовов, 31% времени по cProfile (0.504 сек) и 33% по pyinstrument.
   он ничего не меняет по смыслу: new_dist уже копия dist, а выше стоит
   if candidate < dist[i][j], так что min всегда возвращает то же значение.
   если просто убрать эту строку, время падает с 0.77 до 0.50 сек, то есть она
   стоит около 35% от всего времени.
3. полная копия матрицы на каждом шаге k: 200 копий по 200 строк. отдельно это
   0.046 сек, около 6%. копия нужна автору, чтобы обновлять матрицу не на месте,
   но для floyd-warshall это не требуется: на шаге k значения dist[i][k] и
   dist[k][j] измениться не могут, поэтому обновление на месте даёт тот же ответ.
4. генерация графа не при чём вообще - 0.0005 сек, меньше 0.1%. оптимизировать
   там нечего, но порядок вызовов random надо повторить дословно, иначе получится
   другой граф и другой ответ.

## Итерация 1

**Узкое место:** 8 млн вызовов min, которые ничего не делают, и 200 полных копий
матрицы. вместе это примерно 40% времени.

**Что изменено:** выкинул строку с min и копирование, матрица обновляется на
месте. заодно вынес dist[k] и dist[i] в локальные переменные до внутреннего
цикла, чтобы не индексировать внешний список 8 млн раз. алгоритм и асимптотика
те же, O(n^3). функция shortest_paths_inplace в hw06/optimized.py.

**Время после оптимизации:** 0.255 сек

**Ускорение:** 3.0x

после этого профиль стал плоским: 100% времени внутри самой функции, вызовов
внутрь больше нет, то есть дальше нечего убирать вызовами - надо убирать сами
итерации.

## Итерация 2

**Узкое место:** сами итерации внутреннего цикла. граф разреженный - 600 рёбер на
200 вершин, и матрица заполняется постепенно. если d[i][k] равен бесконечности,
то d[i][k] + d[k][j] тоже бесконечность и ни одну клетку строки i улучшить нельзя.
посчитал прямо: конечными оказываются только 15464 пары (i, k) из 40000, то есть
38.7%. остальные 61% внутренних проходов по 200 элементов - чистая трата.

**Что изменено:** проверка if d_ik == INF: continue перед внутренним циклом. это
классический приём для floyd-warshall на разреженных графах, худший случай всё
ещё O(n^3), но на нашем графе выполняется около 39% работы.
функция shortest_paths_skip_unreachable.

**Время после оптимизации:** 0.110 сек

**Ускорение (от оригинала):** 7.1x

## Итерация 3

**Узкое место:** остались 3 млн итераций внутреннего цикла, и каждая всё равно
стоит десятки наносекунд интерпретатора. индексация списка и сравнение float в
питоне дороже самой арифметики в разы.

**Что изменено:** матрицу перевёл в numpy и заменил два внутренних цикла на одну
векторную операцию: np.minimum(dist, dist[:, k, None] + dist[k], out=dist).
остался только внешний цикл по k - 200 итераций питона вместо 8 млн. вся работа
уходит в C, память непрерывная, out=dist убирает лишнее выделение.
функция shortest_paths_numpy, её и вызывает optimized_run.

**Время после оптимизации:** 0.0092 сек

**Ускорение (от оригинала):** 84x

профиль после: 0.011 сек под cProfile, из них 0.008 сек в самой функции (это
200 вызовов np.minimum), 0.002 сек генерация графа, 0.001 сек np.array.
теперь узкое место переехало в генерацию данных и конвертацию, то есть
оптимизировать алгоритм дальше смысла нет.

## Numba/Cython ускорение (задание 6.2)

**Что ускорено:** исходный тройной цикл из src/slow_code.py целиком, вместе с
копией матрицы на каждом шаге k и вызовом min. алгоритм не менял и на numpy не
переписывал: та же логика, только вход и выход - массив numpy вместо списка
списков, потому что njit умеет работать с типизированными массивами.
функция _floyd_warshall в hw06/accelerated.py.

**Подход:** Numba @njit(cache=True)

**Время:** 0.0092 сек (первый вызов 0.46 сек, из них почти всё - компиляция)

**Ускорение (от оригинала):** 84x

**Ускорение (от optimized):** 1.0x

**Почему numba ускоряет.** цикл в cpython на каждой итерации делает много работы
мимо арифметики: достаёт объекты по ссылкам, проверяет типы, создаёт новый объект
float на каждое сложение, считает ссылки. numba проходит по байткоду, выводит
типы (здесь всё сводится к float64 и int64), и отдаёт llvm обычный машинный цикл
по непрерывной памяти - без объектов, без проверок типов, с регистрами и
векторизацией. поэтому лишние 8 млн min и 200 копий матрицы, из-за которых
питон терял 40% времени, в скомпилированном виде почти бесплатны: min по двум
float64 превращается в одну инструкцию, копия строки - в memcpy.

**Когда подход оправдан.** когда узкое место - это плотный численный цикл с
простыми типами, который нельзя красиво выразить через векторные операции: шаги
зависят друг от друга, есть ранние выходы, нетривиальные условия внутри. тогда
njit даёт скорость C почти без переписывания кода. плюс это дешёвый способ
ускорить чужой код, который трогать не хочется.

когда не оправдан: код на питоновских объектах (словари со смешанными типами,
классы, строки, ввод-вывод) - numba свалится в object mode и выигрыша не будет;
функция вызывается один раз на маленьких данных - компиляция дороже самой работы;
задача уже хорошо ложится на numpy или pandas - там та же скорость C без новой
зависимости и без варианта получить ошибку типизации только в рантайме. наш
случай как раз такой: 84x у numba и 84x у numpy, то есть на этой задаче njit
догнал векторизацию, но не обогнал.
